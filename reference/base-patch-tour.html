dsh-base patch tour

The base bundle's cordis.patch.yml is the closest thing this repo has to a "definition of the product" — ~90 rows that every base-backed profile shares. This page walks it region by region. Open the file beside this page and read along.

How to read it

Rows share one shape: - id: <key> · name: '<pkg>' · optional config: · optional disabled: !!js …. Row order is for readers — fibers activate in dependency order, so you can read the file as grouped capabilities, not a sequence.

Reading one row properly

- id: tool-bash
  name: '@deepseek-ai/dsh-tool-bash'
  disabled: !!js process.platform === 'win32'
  • id: tool-bash — the stable handle. Other patches (profile, home, --patch) address this row by id; the registry and diagnostics report by it.
  • name: — the module specifier the Loader resolves to a package/plugin.
  • disabled: — a !!js predicate; tool-bash and tool-pwsh are platform-gated so only the OS-appropriate one mounts.

Why the "spine" rows sit where they do

The first ~90 lines front-load the services every other plugin injects — llm, session, typert, agent — not because order matters at runtime (it doesn't), but because a reader should meet the foundation before the decoration. The file's comment says it outright: "the grouping is for readers." Reading top-to-bottom is a guided tour from most-fundamental to most-specialized.

The config payloads

Some rows carry inline config: — small, deployment-varying values the plugin's Config schema validates at mount:

  • session-title/session-title-llm — title-generation bounds (max words, byte caps, timeouts).
  • hmr — root: [], which module roots hot-reload watches.
  • agent-default-model — the default provider/model route the launcher proposes.

Everything else takes defaults — a row with no config runs on the plugin's schema defaults. The rule (per AGENTS.md): deployment-varying choices are config, never a hidden constant — so anything you might tune per-profile is reachable from a patch.

Try it

Run dsh --profile web --dump-config and diff the output against this file — you'll see the bundle layer verbatim, then the web-app layer's inserts, then any user patches on top. That output is the running tree.
