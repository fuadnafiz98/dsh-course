cordis.yml, patches & profiles

You've seen that running a plugin creates a fiber. Now the question before it: who decides which plugins get mounted, and with what config? In dsh the answer is never code — it's a stack of YAML patch layers. This lesson teaches you to read that stack.

A patch row, exactly

Read the header comment of dsh-base's patch — it's the best-written documentation in the repo. Its rows look like:

- insert:
    - id: plugin-manager
      name: '@deepseek-ai/dsh-plugin-manager'
      disabled: !!js "!ctx.get('profileContext')"     # only on real launches

    - id: hmr
      name: '@deepseek-ai/dsh-hmr'
      disabled: !!js "!ctx.get('profileContext')"
      config:
        root: []

    - id: llm
      name: '@deepseek-ai/dsh-llm'

    - id: tool-bash
      name: '@deepseek-ai/dsh-tool-bash'
      disabled: !!js process.platform === 'win32'    # bash needs a real shell

Three things to notice:

  • disabled is a predicate, not just true/false. !!js "!ctx.get('profileContext')" means "skip this row when there's no profile context" — i.e. on --dump-config dry-runs, plugin-manager and HMR don't exist.
  • !!js is real JavaScript, evaluated at load time with the boot-time context available as ctx. It's how platform gating (process.platform), environment reading, and "only when launched for real" are expressed declaratively.
  • config is opaque YAML handed verbatim to the plugin — the plugin's Config schema validates it at mount, so a bad value fails loud at boot, not mid-turn.
The one rule

A patch replaces a row's whole config — it does not merge into it. This is why mode-specific config lives in mode bundles, not in dsh-base: a row can only ever have one config value, and the last patch layer to address that row's id wins.

Where the root file fits

There's one subtlety: the profile's actual cordis.yml on disk is literally [] — an empty list — and prepareProfile() rewrites it to [] on every boot. Why? Because everything arrives via patches, and the Loader needs a real file on disk only to anchor module resolution (baseUrl). The comment on lines 152–164 explains it precisely: letting plugin self-disposal write back to the root would bake bundle inserts into the file and duplicate them next boot.

Mental model

Think of the root cordis.yml as a projection, not a source. The source of truth is the patch stack; the root file exists because the Loader needs a filesystem anchor and a place to write back runtime mutations. dsh deliberately keeps it empty so patches stay the only composers.

Profiles are just "which bundles"

A profile is a directory under $DSH_HOME/profiles/<name>/ containing dsh.profile.yml (bundle list) and cordis.patch.yml (the user's own rows). The shipped templates are in packages/bundle/*/:

  • web = dsh-base + dsh-web-app (HTTP server, host rows, ~60 client rows)
  • headless = dsh-base + dsh-headless (a one-shot runner)
  • sdk = dsh-base + dsh-sdk-app (JSON-RPC server)
  • sdk-minimal = dsh-sdk-minimal only — deliberately skips dsh-base, the minimal embeddable tree
  • acp = dsh-base + dsh-acp-app (Agent Client Protocol)

So "dsh web vs dsh headless" is literally "which bundle stack". Same engine; the outermost rows differ.

Go deeper: the Loader + Include split

Two vendored packages cooperate: Loader (vendor/loader/src) turns entry rows into fibers — it resolves module specifiers through the package-resolution layer (dsh-plugin-packages), handles disabled predicates, and maintains the tree. Include (vendor/include/src) parses a cordis.yml into rows and applies patch lists — it's the pure-YAML half. Keeping them separate means patch semantics (last-write-wins, insert, replace) are testable without any module loading. The product-level API is boot() in packages/boot/app-boot — it creates the root Context, mounts Loader, hands the composed tree to Include, waits for settlement.

Go deeper: what --dump-config actually shows

dsh --profile web --dump-config boots just far enough to compose the tree — it mounts Loader, applies all patch layers, prints the effective cordis.yml, and exits before any plugin's apply() runs. That's why !!js "!ctx.get('profileContext')" rows vanish in dumps: no profile context is provided in dump mode. It's the fastest way to answer "what would this profile actually load?" — do it before reading code.

Retrieval You want to disable tool-bash for your own profile without touching dsh-base. Where does that edit go?

Patches address rows by id; later layers win. Your profile patch is layer 2 — it overrides the bundle layer for that row. (A --patch overlay would also work, but it's for per-invocation, not durable profile config.)

Retrieval Why is the profile root cordis.yml always []?

Composition lives entirely in patch layers. The empty root is a deliberate projection — written each boot — so plugin-driven write-backs never duplicate bundle inserts.
