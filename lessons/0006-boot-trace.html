Boot trace: dsh web

Let's walk a real launch end to end, file by file. This is the "read these in order" answer to how does a running dsh actually come to exist? — and the moment where composition (lesson 5) meets the Cordis runtime (lessons 2–4).

The route map

Stage 1 — the bin is just a dispatcher

runCli() parses process.argv into an invocation.mode and dispatches. Four modes: profile (the default — run something), plugin (manage plugin packages), dump-config, dump-config-schema. That's it — no pipeline lives here. For dsh web, mode is 'profile' with profile: 'web', and control passes to runProfile().

Stage 2 — composeProfile(): layers, not code

composeProfile() assembles the patch stack from lesson 5: the profile's bundle patches (in order), the profile's own cordis.patch.yml, the home-level patch, and any --patch overlays — plus a runtime resolution computed before any plugin imports.

Stage 3 — runProfile(): launch facts + the boot call

runProfile() does everything the process owns before the plugin tree gets a say:

  • installs the launch-environment proxy (Node's fetch won't read a .env-declared proxy on its own)
  • registers SIGTERM/SIGINT → bounded shutdown
  • installs the fail-loud handler: any unhandled rejection or uncaught exception is a fatal, labelled exit — because "silently wrong" is worse than "loudly dead"
  • builds ProfileContext — the launch facts every plugin can read: name, dir, patchPath, startedBundles, cwd, home, overlays…
  • calls boot() with a prepare callback that runs after Loader is mounted but before any config row.
Why the ordering matters

The prepare callback provides profileContext, the launch environment snapshot, PluginPackages (module resolution), and cmdlineArgs — before a single patch row mounts. That's what makes !!js "!ctx.get('profileContext')" work in patch files: the facts the expressions consult exist before the expressions run.

Stage 4 — boot(): Context → Loader → Include → audit

boot() is short and surgical:

  1. const ctx = new Context() — the root world (lesson 2).
  2. A diagnostics context captures warn/error logs for the startup report.
  3. ctx.baseUrl = … — anchors relative module resolution at the config dir.
  4. A global internal/update hook observes discarded fiber restarts.
  5. await ctx.plugin(Loader) — the Loader is itself a plugin; mounting it gives the context ctx.loader.
  6. await prepare?.(ctx) — the launcher's setup (stage 3's callback).
  7. mountRootInclude() — mounts the cordis:include builtin against the composed tree; this is what actually reads the YAML and starts spawning fibers.
  8. await ctx.get('loader')?.await() — wait for every row's mount to settle.
  9. auditStartupEntries() — check that the required ids activated; a required FAILURE is a StartupError.

Stage 5 — fibers do the rest

Once Include reads the tree, the Loader creates a fiber per row — and from here, lesson 3's machinery takes over entirely. No orchestrator sequences the mount; dsh-llm's fiber goes PENDING until its injects exist, webserver waits on what it needs, and the tree activates in dependency order. The web profile's extra rows (webserver, the typert gateway, the host API, the client-plugin rows) are just more entries in the same mechanism.

Then boot() returns the root ctx, runProfile() hands the process's lifetime to whatever plugins are alive, and the app runs until something disposes the tree — a webserver plugin holding a listener keeps the event loop alive; a headless-runner disposes the tree when its one task finishes.

Go deeper: the startup audit, exactly

auditStartupEntries doesn't require "everything activated" — it requires a specific id list (agent-loop, webserver, modules, connection, headless-runner, acp, sdk-jsonrpc-server) that defines a usable app to be ACTIVE if present and enabled. Optional failures warn; required failures throw StartupError with the whole inactive-entry report — including "pending (waiting for service: X)" rows that tell you exactly which dep never arrived. It's the difference between "plugin didn't load" and "plugin didn't load because it was waiting for ctx.shell".

Go deeper: disposal on boot failure

If anything after new Context() throws, boot's catch awaits ctx.fiber.dispose() — the root fiber's disposal cascades to every mounted child, so a half-booted app tears down cleanly instead of leaking listeners and timers. The error is then wrapped with a stage label (host preparation failed vs plugin tree failed to load) so the report says where boot died, not just that it did.

Retrieval In dsh web, which code actually reads the YAML and mounts the plugin rows?

The launcher and boot() only prepare the ground. Reading the composed tree and turning each row into a fiber is Include+Loader's job — the same machinery that would mount a plugin added at runtime.

Retrieval Why does runProfile() provide profileContext inside a prepare callback rather than before boot()?

Exactly — ctx doesn't exist before new Context() inside boot, and the !!js predicates in patch rows consult ctx.get('profileContext') as they mount. The prepare callback is the only slot that is both post-Context and pre-tree.

Primary source Re-trace this path yourself in the editor: bin.ts → profile-boot.ts → app-boot/index.ts (boot → mountRootInclude → auditStartupEntries). Then run dsh --profile web --dump-config and match a few rows to the plugins you now know.
