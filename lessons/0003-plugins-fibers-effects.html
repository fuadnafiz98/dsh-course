Plugins, fibers & effects

A plugin in Cordis is just "something callable with a context and a config." A fiber is the runtime bookkeeping for one mounted plugin — its lifecycle, its dependencies, everything it registered. This lesson is the heart of Cordis: once you see fibers, the whole codebase stops looking like magic.

What a plugin looks like

Three shapes, all equivalent at runtime (registry.ts — the Plugin union):

// 1. a function — mount it with 'apply'
function plugin(ctx, options) { ctx.on('ready', () => ...) }

// 2. an object with 'apply' — the most common form
export default {
  inject: ['sessions', 'llm'],          // ← wait until these services exist
  apply(ctx, options) { ... }
}

// 3. a class — gets 'new'-ed, good for Services
export default class Foo extends Service {
  static inject = ['sessions']
  constructor(ctx, options) { super(ctx, 'foo'); ... }
}

A real plugin from the product — the agent-loop row:

export default {
  name: 'dsh-agent-loop',
  inject: {
    required: ['agents', 'sessions', 'llm', 'systemPrompt'],
    optional: ['agentConcurrency', 'agentRetry', 'storageQuota'],
  },
  apply(ctx) {
    ctx.plugin(ReactLoopAgent)          // ← mount ANOTHER plugin, with extra deps
    ctx.effect(() =>                    // ← register a factory; auto-undone on unload
      ctx.agents.registerFactory((ctx, options) => new ReactLoopAgent(ctx, options))
    )
  },
}

inject — the load-order mechanism

Here's the problem: row order in cordis.patch.yml doesn't guarantee anything. If tool-bash is listed before tools, the naive "mount in file order" breaks. Cordis's answer: don't order rows — declare what you need and let the framework sequence mounting for you.

When a plugin declares inject: ['tools'], its fiber enters a PENDING state and stays there until something provides ctx.tools. The moment the service exists, the fiber activates and the plugin runs — and the declaration becomes a runtime guarantee: by the time your code executes, every required service is live.

The fiber state machine

Fiber is the single most important class in the vendored runtime (fiber.ts). Its states:

StateMeaning
PENDINGInjected services not all present yet — waiting (or config not resolved)
LOADINGConstructor/apply is running right now
ACTIVEPlugin mounted; its effects, listeners, and services are live
FAILEDConstructor threw — fiber stays up so errors are diagnosable, but provides nothing
UNLOADING → DISPOSEDEffects being reversed; then the fiber is gone

Two transitions are subtle and worth internalizing:

  • A service disappearing unloads its dependents. If the tools fiber unloads, every fiber that declared inject: ['tools'] is torn down too — and re-mounts fresh if the service comes back. That's how hot-reload propagates.
  • Config changes re-create the fiber. Patches replace a row's whole config; a change is applied as "dispose old fiber, spawn new fiber" — never in-place mutation.

ctx.effect() — the undo contract

Cordis's central invariant: everything a plugin registers must be unregisterable. The mechanism is ctx.effect(fn) — it runs fn now and records whatever disposer it returns on the current fiber. On unload, Cordis runs all recorded disposers in reverse registration order (fiber.ts:434-497).

ctx.effect(() => {
  server.listen(port)
  return () => server.close()    // ← called automatically when this fiber unloads
})

You rarely write this yourself: ctx.provide(), ctx.on(), ctx.plugin(), ctx.intercept() are all built on effect(). The whole app is a nested set of paired setup/teardown operations, which is precisely what makes "replace a plugin at runtime" possible.

The takeaway

Fibers are what make the tree live. A fiber owns: the plugin function, the resolved config, the inject declarations it's waiting on, and a stack of disposers. "Mount a plugin" = create a fiber. "Hot-reload" = dispose a fiber and create a new one. "Shutdown" = dispose the root fiber, which cascades to everything.

How a row becomes a fiber

  1. Loader sees an entry { name: '@deepseek-ai/dsh-tools', config: {...} } and calls ctx.plugin() for it.
  2. Registry resolves the module specifier to an import, creating a Fiber.
  3. The fiber reads the plugin's inject static; deps absent → PENDING.
  4. Deps arrive → start(): resolve config (interceptors first), call the plugin inside a child context, flip to ACTIVE.
  5. Inside apply(), every ctx.on/provide/plugin/effect is appended to this fiber's disposer stack.
Go deeper: volatile config and fiber reuse

A local modification in vendor/README.md documents volatile config: if a plugin's config changes in ways that don't require re-mounting, a fiber can update in place rather than full dispose/recreate. This is how config schemas merged via intercept() stay cheap. Read Fiber.update() with this lens: update is invoked on every dep/config change and decides between "wait more", "reuse", and "full restart".

Go deeper: failure is a state, not a crash

If apply() throws, the fiber moves to FAILED but doesn't vanish — it stays in the tree so dsh --profile web --dump-config, the web UI's fiber list, and logs can all inspect why. It's also what makes "one bad plugin doesn't kill the app" true: dependents just never see the service.

Retrieval tool-bash is listed before tools in the patch. Is that a bug?

Row order is cosmetic for humans. The fiber system makes mount order an emergent consequence of the dependency graph — tool-bash stays PENDING until the tools service exists.

Retrieval Your plugin calls ctx.on('ready', ...). What keeps that listener from leaking after your plugin unloads?

Every registration API on ctx is implemented on top of ctx.effect(). Unloading a fiber runs its recorded disposers in reverse order, automatically undoing listeners, provides, child plugins, everything.
