The shape of dsh

Before we open a single source file, you need the one idea that makes this entire codebase legible: there is no "main program" to find. The harness is a tree of plugins assembled from YAML, and every feature — the model adapter, the tool registry, the session log, the agent loop itself — is just a row in that tree.

What a "harness" even is

A language model is a function that takes messages and returns a stream of text. By itself it can't do anything — it can't run commands, read files, or remember yesterday's conversation. An agent harness is all the machinery around the model that turns "I predict the next token" into "I am a coding agent":

  • a loop that sends messages to the model and feeds tool results back,
  • tools the model can call (bash, file reads, web search…),
  • a session log that records everything so a crash never loses the conversation,
  • safety rails — sandboxes, approval prompts, timeouts,
  • and surfaces — a web UI, a headless CLI, an SDK — for humans and other programs.

Most harnesses hardcode this pipeline. DeepSeek Harness makes a radical choice instead: every one of those pieces is a plugin, loaded from configuration, replaceable from configuration, removable from configuration.

Everything is a plugin — literally

Open packages/bundle/base/cordis.patch.yml. That file is the closest thing this repo has to a "main". It is a list of rows like:

- id: tools
  name: '@deepseek-ai/dsh-tools'

- id: tool-bash
  name: '@deepseek-ai/dsh-tool-bash'
  disabled: !!js process.platform === 'win32'

Each row says: mount the package named name, with this config, unless disabled. The session store, the LLM adapter registry, the bash tool, the subagent system, telemetry — all just rows. There is no privileged core to patch because the core is rows too.

Mental model

Think of the running harness as a Christmas tree, not a car engine. A car engine is machined as one block; if a part fails you can't swap it mid-flight. A Christmas tree is a trunk plus ornaments — every ornament hangs on a hook (a ctx.* service or an event), and you can replace any ornament without touching the others. Cordis is the trunk and the hooks.

The five layers you'll always be in

Every file in the repo belongs to exactly one of these layers. When you're lost, first ask "which layer is this file in?" — the answer tells you what the file is allowed to do.

Reading the repository

The repo is a pnpm monorepo. The directories you'll actually live in:

PathWhat's inside
vendor/Source-vendored Cordis + its foundation libraries (cosmokit, schemastery, loader, include, hmr…). The framework, owned and auditable in-repo.
packages/<group>/<pkg>/~200 packages of the form @deepseek-ai/dsh-<name>, grouped by capability family. The product.
apps/Launched applications: cli (the dsh bin), web (the browser frontend), desktop.
docs/The documentation system — architecture map, subsystem references, cookbooks, postmortems, decision notes.
snapshots/Keyless recorded-session tests: canned model streams replayed through the real shipped profiles.
.agents/Agent-facing workflows and the notes archive — the decision records explaining why the code looks this way.
Go deeper: why vendored Cordis?

Cordis is copied into vendor/ rather than depended on from npm, so the harness owns its framework layer: auditable, patchable, pinned. The manifest of what's vendored, from which upstream commit, is in vendor/README.md — and its "Local modifications" list (22 entries at this commit) is a fascinating read: it tells you exactly where the harness hardened upstream Cordis (reentrant disposal, lazy config resolution, volatile config, Node loader internals…). When you read vendor/cordis/src, you're reading upstream Cordis plus those patches.

Go deeper: "spatiotemporal composability"

The README cites a paper — A Programming Paradigm for Spatiotemporal Composability — which is Cordis's theory: plugins compose in space (contexts and scoped realms) and time (fibers that load, unload, and hot-reload without dropping the world). You don't need the paper to use the codebase, but it's the reason effects and scopes exist.

Your first five-minute task

Prove the "everything is a row" claim to yourself:

  1. Open the llm row in dsh-base — one line mounts the model-adapter registry.
  2. Open the tool-bash row — the model-facing bash tool is a row you could disable.
  3. Open the headless patch — see how a whole different product (one-shot CLI) is just ~5 extra rows on the same base.

If a feature isn't in a patch or a plugin's source, it doesn't exist at runtime. That invariant is your compass for the rest of the course.

Retrieval A new coworker asks where "the main function" of dsh lives. What's the honest answer?

Exactly. bin.ts is only the launcher: it parses argv, resolves the profile, and hands a composed YAML tree to the Cordis Loader. The "program" is the set of rows that tree ends up mounting — swap the rows, and a different product runs. Even the agent loop is just the dsh-agent-loop plugin.

Retrieval Which layer decides which plugins exist in a running app?

The composition layer owns membership. dsh-base inserts ~80 rows; a profile like web layers more bundles and patches on top; a user's cordis.patch.yml and --patch overlays get the last word.
