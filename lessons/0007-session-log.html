The session log

The single most important architectural decision in the harness: a session is an append-only event log, and everything else — the model's context, the UI's transcript, replay, resume — is a projection of it. There is no "conversation object" being mutated. There is a log. This lesson teaches you to read it.

The core invariant

The rule everything obeys

Model-visible ⟺ logged. Anything that reaches a model request must be reconstructable from the session log. If it's not an event, the model never saw it — and if the model saw it, it's an event. This one rule makes crash-resume, replay testing, and UI rendering all the same mechanism.

The log and the surface are two different things

Inside SessionEventMap there are ~14 event types, but only five produce model-visible messages. The split is the key idea:

Why split log and surface?

Because the model should never see bookkeeping. A step/start matters to replay and the UI; it's meaningless to the model. And when a conversation outgrows the context window, you want to say "replace these 40 messages with this summary" without rewriting history — the old events stay in the log (so resume and audit still work), but the surface swaps which nodes the model sees.

What this buys the whole system

  • Resume for free — a crashed session's log is the state; reopening it replays events and the next step picks up mid-turn (an orphaned open turn is closed with interrupted).
  • Replay for testing — recorded logs feed the snapshot harness; canned streams drive the real loop.
  • The UI for free — the web transcript is just "render the log's surface + lifecycle events".
  • Fork/subagent seeding — buildForkSeed copies a prefix, tags the cut with session/end-seed, and the child diverges from there.
  • Compaction — replace a span of surface nodes with one summary node, keeping the log intact underneath.
Format version

The log is durable on disk, so its format is versioned: SESSION_FORMAT_VERSION = 4 (types.ts:89). The rule for bumping it is unusually strict — only structural changes (header, envelope, core event semantics, the surface mechanism) bump; a new ordinary event type does not, because the ignorable envelope guard covers vocabulary growth. This discipline is what makes "the log is the truth" safe across versions.

Go deeper: the surface op mechanism

A surface event doesn't just appear — it carries a surfaceOp describing how to place it: append as a new node, replace an existing node's content, or clear nodes. A SessionMessageProjection (surface.ts:35-46) is the plugin-owned interpreter for an event that changes existing messages — compaction uses it to swap a span of nodes for a summary without touching the log. The surface is a materialized view; the log is the database.

Retrieval The model's context for the next request is derived from…

No mutable conversation exists. deriveMessages reads the log's surface nodes in order; compaction and prompt updates are surface ops over those nodes.

Retrieval A model call fails mid-stream and the step retries. Where does the failed attempt go?

The rule is "everything model-visible is logged" — and a failed attempt is real history. assistant/attempt preserves its stream so the log stays lossless; it just doesn't contribute a surface message.
