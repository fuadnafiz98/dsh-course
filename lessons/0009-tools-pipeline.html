The tool pipeline

A model produces a block like {name:"bash", arguments:"{\"cmd\":\"ls\"}"} — and the harness has to turn that into a real side effect, safely, durably, and in a way plugins can control. That's the tool pipeline: a registry (ctx.tools), a scheduler (executeToolCalls), and a chain of waterfalls around every single call.

Two files, two jobs

FileJob
packages/core/tools/src/index.tsToolRuntime — the registry (ctx.tools) and the per-call policy pipeline (pre-execute → execute → post-execute).
packages/core/agent-loop/src/tool-calls.tsexecuteToolCalls — the step's scheduler: barriers, bounded parallelism, model-ordered commits, cancellation.

Keep them separate in your head: the scheduler decides when and in what order; the runtime decides what happens around each call.

What a tool is

A tool is a plugin that registers a ToolDefinition on ctx.tools — schema (name, params, description the model reads), an execution mode, and the body that runs it. The bash tool is the canonical example — it's just a row in the patch (id: tool-bash) whose plugin calls ctx.tools.register(...). Nothing is special about it; the model-facing "bash" is literally a plugin you could unmount.

Per call: the waterfall sandwich

Every tool invocation passes through three waterfalls plus an observability emit (the event map):

  • tools/pre-execute — admit or veto before the body runs. Approval prompts ("may I run this command?") and guards hook here.
  • tools/execute — wraps the body itself. A timeout policy (dsh-tool-call-timeout-policy) is literally a tools/execute wrapper that races the body against a clock.
  • tools/post-execute — reshape the committed result before the model sees it (content projection, redaction).
  • tools/result — an emit, not a waterfall: the frozen outcome for observers/UI, after which the loop appends the durable tool/result event.

The scheduler: barriers + bounded parallelism

executeToolCalls (tool-calls.ts:60-102) groups a step's calls by their live execution mode:

  • exclusive — a barrier: runs alone, waits for everything in flight to finish first (e.g. a tool that changes working directory).
  • parallel — a rolling pool bounded by agentLoop.config.maxParallelToolCalls; calls dispatch overlapping but results always commit in model order.

Two guarantees make it durable instead of clever:

  • Model-ordered commits. The commitReady() loop only appends a tool/result once every earlier slot has settled — so the log's tool/result order always matches the order the model requested, even when executions finish out of order.
  • Abort is honest. On cancellation, started calls drain and commit their real results; calls that never started get a synthetic tool/result (appendSkippedToolCall, tool-calls.ts:249-260) so the log stays valid for replay — the model's call always has a matching result.
The rule

The session log's invariant — every model-visible call has a matching result — is enforced by the scheduler. It's why a cancelled turn still replays cleanly: skipped calls get recorded error results rather than dangling.

Scoped tools — the seam under presets

ToolRuntime isn't a flat map — it's ScopedLayers (index.ts:833): registrations can be global or scoped to an agent's scope key. So two agents in one process can see different tool sets — a subagent with a read-only subset, a PTC agent presenting only run_code. That's the same isolate/realm machinery from lesson 2 surfacing at the tool layer, and lesson 11 builds on it.

Go deeper: the scheduler's staged API

The runtime exposes an internal [TOOL_RUNTIME_SCHEDULER] staging view with prepare / dispatch / finalize / finish (index.ts:815-821). prepare runs the pre-execute stage and can short-circuit a call to a post-result or final-result without ever dispatching the body — that's how a guard denies a call cleanly while still producing a well-formed result.

Go deeper: presentation vs execution

The result the model gets and the card the UI renders are different concerns. A tool can attach a private meta payload to its tool/result (e.g. a result-time diff) that persists verbatim — opaque to the core — and a presentResult hook reads it back to reproduce the same card on replay. Model-facing contract and UI presentation stay separate by design.

Retrieval The model asks for 5 parallel tool calls and a user hits cancel mid-flight. What reaches the log?

The scheduler drains started calls and appends synthetic results for the rest — every model-visible tool/call pairs with a tool/result, so the log stays replayable.

Retrieval Where would an "approve before running bash" feature hook in?

Approval must precede the side effect — tools/pre-execute is the admit/veto waterfall. Post-execute only shapes results after the fact.
