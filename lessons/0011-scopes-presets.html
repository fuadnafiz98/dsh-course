Scopes, realms & presets

So far, every agent has shared the same services. But a real product needs different agents in one process: a main agent with every tool, a read-only subagent, a custom persona with its own prompt and tool subset. That's the per-agent world — built from Cordis's isolate, the scope primitive, and the preset system.

The problem: one process, many agent identities

A subagent that shouldn't run bash can't just have a "bash disabled" flag — the service ctx.tools is global. Deleting bash from it would break the parent. What's needed is a way to say: "for this agent, ctx.tools resolves to a different registry." That's the realm mechanism from lesson 2, made practical.

Layer 1 — isolate realms fork service resolution

Recall ctx.isolate('tools', Symbol()): it creates a child context where the tools name resolves under a fresh realm key. A provider mounted inside writes that private key — visible below the child, invisible to the parent. The parent and the child now have two different ctx.tools that happen to share a name.

Layer 3 — ScopedLayers: registries that shadow

Services that need per-scope state build on ScopedLayers (scope/src/store.ts) — a scope-keyed map where a scoped registration shadows the global one. That's exactly what ToolRuntime uses: the global layer holds every registered tool, and an agent's scope layer can register a smaller set the model sees instead. ctx.emit('tools/change') fires whenever a layer changes, so the prompt's tool schemas stay live.

Layer 4 — presets compose a per-agent world

A preset (dsh-agent-preset-registry) is a named bundle of capabilities for composing one agent: which plugins mount in its scope, which persona/prompt sections, which tool subset. When a session creates an agent, the preset registry mounts a small subtree inside that agent's scope — so the agent's world is literally a plugin tree scoped to itself.

ctx.agents.create({ preset: 'reviewer', provider, model, session })
//   → mounts the 'reviewer' preset's subtree inside a fresh scope
//   → that agent's ctx.tools / ctx.compaction / prompt are its own
Why presets exist

Presets are the answer to "how do I ship a specialized agent?" — a code reviewer, a read-only explorer, a plan-mode agent — as composition, not code. The preset is a list of plugins and config; the scope makes it isolated. New agent type = new preset, not a fork of the loop.

Where you see it

  • Subagents — a spawned/forked child gets a scope; its tools and prompt can differ from the parent's.
  • PTC mode — an agent scoped to "only run_code" is a scope-layered tool registry, not a special code path.
  • Plan mode / personas — prompt sections and tool subsets per agent preset.
  • Scoped events — the UI subscribes to one agent's agent/* feed by scope key.
Go deeper: scope parents and rebinding

Scope keys can form a parent chain via linkScopeParent — a child scope's registry view inherits down, and an event listener tagged with an ancestor receives descendant events. ScopeParentBinding.rebind() can re-link a key — used by "blank-session recompose": when a session's composition is rebuilt, its scope is re-parented so retained views keep resolving. This is subtle machinery; you only need it when implementing a scope-aware service.

Go deeper: the durable record

A session's preset is persisted in SessionHeader.agentPreset (types.ts:124-131). Why durable? Because the preset decided the tools and prompt — resuming a session under a different composition would replay history the current model can no longer act on. The header pins which composition made the history.
