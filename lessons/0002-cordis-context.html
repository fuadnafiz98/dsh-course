Context: the shared world

Everything in Cordis hangs off one object: the context, always named ctx. It's a service directory, an event bus, and a plugin launcher in one. This lesson is about its first job — how services get onto ctx and how other plugins find them.

ctx is a directory, not a god object

When you write ctx.tools or ctx.llm, you're not touching a hardcoded property. Context instances are wrapped in a JavaScript Proxy: a read of ctx.<name> is forwarded to the reflect layer, which looks up which plugin currently provides a service under that name and returns it.

// vendor/cordis/src/context.ts — the root context wires itself up
const self = new Proxy<this>(this, ReflectService.handler)
this.root = self
this.reflect = new ReflectService(self)   // the service store
this.registry = new RegistryService(self) // ctx.plugin(), ctx.inject()
this.events = new EventsService(self)     // ctx.on(), ctx.emit(), ...
this.logger = new LoggerService(self)
return self                               // callers get the PROXY

— vendor/cordis/src/context.ts:71-84

Two consequences follow:

  • Names are stable, implementations are not. ctx.shell means "whoever currently provides the shell service" — a local executor today, an SSH executor in a different profile. Consumers code against the name, never the class.
  • Reads can fail. If nothing provides ctx.tools, the proxy throws. That's intentional — a missing dependency is a loud boot failure, not a silent undefined — and it's why the next lesson's inject mechanism exists.

How a service gets onto ctx

The base class is Service. Its constructor does the registration for you:

export abstract class Service<T = never> {
  constructor(protected ctx: Context, name: string) {
    ...
    self.ctx.reflect.provide(name, self, this[symbols.check])
    return self   // (possibly a callable instance, e.g. ctx.logger("x"))
  }
}

— vendor/cordis/src/service.ts:42-59

So a real service in the wild — the session store — is:

export class SessionStore extends Service {
  constructor(ctx: Context) {
    super(ctx, 'sessions')   // ← now ctx.sessions === this, for every plugin
    ...
  }
}

— packages/core/session/src/index.ts:925-963

And removal is automatic: the provide() call is recorded as an effect owned by the plugin's fiber. When the fiber unloads (config reload, HMR, shutdown), the service is unregistered with it. Nothing to clean up by hand — lesson 3 goes deep on this.

A real pitfall the codebase documents

ctx.foo (proxy property) and ctx.get('foo') are NOT the same read: the proxy honors per-context isolation realms (below), while ctx.get reads the global store. That's why packages/AGENTS.md says "Optional services use ctx.get(name); reserve ctx.<name> for declared injections." There is an actual postmortem about the day this bit someone.

Child contexts: extend, isolate, intercept

The last piece of Context is that it's a tree, not a singleton. ctx.extend(meta) creates a child that prototypally inherits the parent but owns extra keys:

const child = ctx.extend({ answer: 42 })  // child sees parent's services + its own 'answer'

Two specialized variants matter enormously in dsh:

  • ctx.isolate(name, label) — below the child, the service name resolves in a fresh realm: a provider mounted there doesn't overwrite the parent's service of the same name. This is how two agents in one process get different tool sets or different compaction services — lesson 11 builds the whole preset system on it.
  • ctx.intercept(name, config) — injects extra config into every plugin under the child that consumes service name. It's how inject: { llm: {...} } passes per-plugin config into a shared service.

Where this shows up in dsh

  • ctx.sessions, ctx.tools, ctx.llm, ctx.agents, ctx.systemPrompt — the core spine, each a Service subclass provided by one row in the base patch.
  • Every capability seam — ctx.shell, ctx.fs, ctx.subagents — is the same mechanism, designed so the provider can be swapped per deployment or per agent.
  • Host services like ctx.profileContext are just ctx.provide() calls made by the launcher before the tree mounts (profile-boot.ts:296-304).
Go deeper: how the proxy actually resolves a read

ctx.sessions hits ReflectService.handler's get trap (vendor/cordis/src/reflect.ts). The lookup key isn't the string 'sessions' — it's the realm symbol stored in ctx[Context.isolate]['sessions'] (defaulting to a shared symbol). That indirection is what makes isolate() a one-line realm switch: a child context swaps which symbol 'sessions' maps to, and the same property read returns a different implementation. Reads can also be intercepted: internal/get/internal/set are waterfall events that plugins can hook — the service directory itself is extensible.

Retrieval Plugin B needs the session store. What does it import?

Right. Consumers depend on the service name, never the class. Importing the concrete provider would weld B to one implementation and break the seam the whole architecture exists for.

Retrieval What does ctx.isolate('tools') give you?

Isolation forks resolution, not the service. Inside the child, ctx.tools can be a different registry (a per-agent tool set) while the parent's ctx.tools is untouched. Presets rely on this — lesson 11.
