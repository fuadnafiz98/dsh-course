The LLM seam

The agent loop never imports a provider SDK. It calls ctx.llm.stream(request) or ctx.llm.prepareCall(config) and doesn't know — or care — whether the bytes come from DeepSeek, OpenAI, a local model, or a test fake. That indirection is the LLM seam, and it's the reason the same harness serves any model.

The shape of the seam

LlmRuntime (packages/llm/llm/src/index.ts:342) is just a service named llm holding a registry: provider route → adapter. An adapter is a plugin that knows one provider's wire format; it registers itself at mount and unregisters when its fiber unloads.

Two calls the loop makes

From lesson 8's prepareRequest:

  • ctx.llm.prepareCall(config, signal) — resolves the adapter for the route, validates config, and returns a PreparedLlmCall carrying the adapter's stream(), its retry policy, context-window metadata, and the effective config (adapter defaults folded in). Binding once per step means the adapter's capabilities are known before the request is built.
  • preparedCall.stream(request) (or the raw ctx.llm.stream fallback) — returns the async iterable of stream frames the loop settles into a durable event.

What an adapter actually does

An adapter translates between the harness's canonical message vocabulary and a provider's wire protocol:

  • In: take {provider, model, messages, tools, …} and render the provider's request body.
  • Out: yield canonical stream frames (text deltas, reasoning deltas, tool-call deltas, usage, finish reason) regardless of the wire dialect.
  • Metadata: providerInfo (id/name), providerRetryPolicy, context-window size, system-prompt-update mode.

Registration is an effect (registerAdapter): it's a ctx.effect whose disposer removes the routes — so unloading an adapter plugin unregisters it, and llm/adapters-updated fires for observers.

Why this matters

The LLM seam is the Definition/Provider/Consumer pattern you'll see everywhere in lesson 12. dsh-llm is the definition (the ctx.llm service + adapter contract). Each provider package is a provider. The agent loop is the consumer. Because they only meet through the service, a new provider is a new plugin, not a change to the loop.

The stream is interceptable too

llm/stream is a waterfall — the same middleware mechanism as agent/request. A plugin can wrap the live stream to add telemetry, redact secrets from deltas, or enforce a policy — around the actual model call, not beside it.

Retries are owned by the adapter's policy

When a stream finishes with an error, the loop consults the agent/request-error waterfall carrying the adapter's retryPolicy — an {kind:'retry'} decision re-enters request preparation without re-admitting the step. The retry decision belongs to the provider's declared policy, not a hardcoded loop behavior — one more place the seam keeps provider knowledge out of the core.

Go deeper: the registry is atomic + observable

registerAdapter is all-or-nothing (a duplicate provider route throws DUPLICATE_ADAPTER), validates adapter metadata, and — unusually — fires llm/adapters-updated with each listener contained so one broken observer can't veto a commit or starve the others. The replace() handle re-routes in one synchronous section, so no observer ever sees a half-swapped registry. This is a model for writing your own registries.

Retrieval How does the loop reach DeepSeek's API?

The loop only knows the ctx.llm seam. A DeepSeek adapter plugin registered the deepseek-official/deepseek-flash routes at mount; the loop resolves them by name.

Retrieval What happens to a provider's routes when its adapter plugin unloads?

Registration is a ctx.effect: the disposer deletes the routes and fires llm/adapters-updated. Unloading the fiber un-registers the provider automatically.
