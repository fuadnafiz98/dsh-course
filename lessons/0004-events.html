Events: the five dispatch modes

Services answer "who can I call?" Events answer "who can I notify — and do I want an answer back?" Cordis has five dispatch modes, and learning them is what unlocks the agent loop: the harness's entire policy layer is built on waterfalls.

One bus, five semantics

All listeners are registered with the same ctx.on(name, fn) — (EventsService). What differs is the dispatch mode, a property of the event name (declared once via TypeScript EventMap merging), not of the call site.

Waterfall: the rule that unlocks everything

A waterfall listener has signature (payload, next) => result. To pass control down the chain, it calls next(). To inspect or mutate around the inner call, it can do work before and after:

// a guard that wraps every tool execution
ctx.on('tools/pre-execute', async (call, next) => {
  if (!policy.allows(call.name)) return denied(call)   // ← short-circuit: never reaches the tool
  const result = await next(call)                       // ← delegate; resumes with inner result
  audit.log(call.name, result)
  return result
})

This is the middleware pattern you know from Express/Koa — except here it's a language-level event primitive, and the whole harness's policy surface is built from it:

  • agent/pre-step — "should this step even reach the model?" (budgets, compaction)
  • agent/request — last chance to mutate the outgoing request (headers, plan-mode tweaks)
  • llm/stream — wrap the live stream (telemetry, redaction)
  • tools/pre-execute / tools/post-execute — approval, injection, result shaping
The rule

AGENTS.md enshrines it: "Waterfall listeners MUST call next() to delegate; returning without it short-circuits the chain." That asymmetry is deliberate — a listener that doesn't delegate is the policy. Forgetting next() is the single easiest bug to write, and the codebase's #1 footgun. When a tool call silently never runs, suspect a waterfall hook upstream that returned early.

Go deeper: the event map is TypeScript-mergeable

Event names are typed via declaration merging into EventMap — a plugin that emits 'llm/adapters-updated' merges its payload type into the map, so a ctx.on('llm/adapters-updated', (payload) => ...) gets the right type and a typo'd name is a compile error. The repo's doc convention requires @mode and payload @param JSDoc on every declared event — scan packages/core/agent/src/index.ts to see the pattern. That's also how docs and reference pages stay truthful: the type IS the catalog.

Go deeper: scoped events with keys

Scope-keyed events let a listener subscribe only to events about a specific entity: ctx.on('agent/status', agent.scope.key, fn) fires only for that agent. This is how the UI watches one session without filtering global noise, and it's what the preset/scope machinery (lesson 11) uses to give each agent its own event plane.

Retrieval A tool call needs an approval prompt that can block it. Which event mode?

Approval is interception: you want a chance to prevent delegation, not just observe it. Only waterfall gives you next()-or-don't.

Retrieval Why does the loop's agent/status use emit instead of parallel?

If the loop awaited UI listeners, a slow UI would stall tool execution. Emit means "here's a fact; do with it what you will" — the loop continues immediately.

Primary source Read events.ts top-down — the mode dispatch is a small readable kernel. Then find one waterfall usage: ctx.on('agent/pre-step', ...) in the compaction package is a good one.
