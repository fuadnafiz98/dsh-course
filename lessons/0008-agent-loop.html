The agent loop

Everything so far was scaffolding. This is the driver: ReactLoopAgent in packages/core/agent-loop/src/agent.ts. One object per session, ~690 lines, and — this is the punchline — it's just a plugin. By the end you'll be able to read the whole turn lifecycle as a program.

The vocabulary

TermMeaning
TurnOne "go" at the user's input — may contain many steps. Bracketed by turn/start / turn/end.
StepOne model call + the tool executions it requested. Bracketed by step/start / step/end.

One picture: the whole turn

The phase machine

The driver isn't a loop you await — it's a state machine that runs itself (Phase type):

type Phase =
  | { kind: 'idle'; lastTurn: number }
  | { kind: 'maintenance'; abort; lastTurn; wakeRequested }
  | { kind: 'running'; abort; turn; step; wakeRequested }

idle → running happens inside wakeDriver() (agent.ts:214-235), which spins up one driver task that calls turn() in a while until the inbox is empty. cancel() doesn't kill the driver — it aborts the phase's AbortController, and the driver exits through the normal finally that appends turn/end. That symmetry is why cancellation never orphans a turn in the log.

Step admission — where policy hooks in

preStep() (agent.ts:267-286) is the front door of every step:

  1. Claim input from the inbox lane (next-turn for a fresh turn, next-step mid-turn).
  2. Assemble the prompt — ctx.systemPrompt.assemble() gathers registered sections + tool schemas.
  3. Project runtime context — a synthetic user-role message with cwd, file changes, etc.
  4. Run the agent/pre-step waterfall — any plugin can reject the step ({kind:'reject'} → turn ends blocked) or rewrite the admitted messages. Compaction hooks here.

If the decision is enter, the loop appends step/start and calls step().

Request preparation — the config is a waterfall

prepareRequest() (agent.ts:546-596) builds the call config through another waterfall:

  • Seed config = the agent's declared {provider, model} route + persisted effort settings.
  • agent/request waterfall → plugins mutate the proposal (a plugin could swap the model, cap max_tokens, inject headers).
  • ctx.llm.prepareCall(config) binds the provider adapter — lesson 10. If no adapter exists (NO_ADAPTER), the loop still proceeds with the raw config so middleware can serve it.

Then buildRequest() (agent.ts:599-687) does the durable bookkeeping: appends request/header (initial / resume / change / series), detects tool-registry diffs and logs them as a developer/message, then calls session.deriveMessages() — the exact point where the session log becomes the model's context — and freezes the result into the request.

The stream — and what "settle" means

The model call is a stream; each frame is emitted live as agent/assistant-stream for the UI. But durability is the point: the loop accumulates the stream in an AssistantStreamAttempt and then settles it:

  • Success → assistant/message (surface event: text + reasoning + tool calls + the exact stream + usage).
  • Aborted mid-stream with content → assistant/message with interrupted: true.
  • Failure / empty abort → assistant/attempt — the failed stream, durable, so retry never fabricates history.

That settle step is the "model-visible ⟺ logged" rule in action: whatever the model would see next turn is already an event.

Tool calls and the turn boundary

If the settled message contains tool-call blocks, executeToolCalls() (tool-calls.ts) runs them — that's lesson 9. Each emits tool/call then tool/result. When they finish, the step decides the turn's fate: completed if the model is done, or the loop continues for another step if the model asked for tools. turn/end { reason } is always appended in the finally — even on a throw — which is why the log can never hold an unclosed turn.

The whole lesson in one sentence

The loop is a transaction writer: for each step it claims input → admits via pre-step → prepares config via agent/request → logs the request header → streams → settles an assistant event → runs tools → and always writes turn/end. Every seam is a waterfall; every effect is durable.

Go deeper: the inbox's two lanes

InboxTarget is 'next-turn' | 'next-step'. followup() queues to next-turn (a new turn), steer() to next-step (mid-turn nudge), inject() to next-step without a wake. claim(target) drains a lane. The subtlety — documented in send()'s comment — is that a wake message can't join an aborted activity: it's reclassified to next-turn so a cancellation never swallows fresh input.

Go deeper: the fused dispatch

agentEvents(loopCtx, this) (agent/src/dispatch.ts) builds one object with every agent/* emit/waterfall pre-bound to this agent's scope. Built once in the constructor so hot-path emits don't allocate — a small, deliberate performance choice. Scope-keyed events (lesson 4's scoped subscription) let the UI listen to this agent's stream without filtering a global feed.

RETRIEVAL Where in the loop does the session log actually become the model's context?

buildRequest derives the message list from the session surface and freezes it into the request — the durable log is the single source of the model's context.

RETRIEVAL A plugin wants to reject a step before the model sees it. Where does it hook?

agent/pre-step is the admission waterfall — rejecting there ends the turn as blocked before a request is ever built.

PRIMARY SOURCE Read agent.ts in order — send → wakeDriver → kick → turn → preStep → step → prepareRequest → buildRequest. It's the most important file in the repo; this lesson is your map for it. Then open docs/agent-lifecycle.md — its Mermaid sequence diagram is the same flow from the outside.
